# Дорожная карта реализации — ИИ-агент «Хермес» (Mironov)

9 этапов от настройки базовой агентной оболочки до прод-готовности на VPS. Каждый
этап заканчивается **демонстрируемым результатом** (что можно потрогать руками).

Ключевая идея: **MVP-first**. Этап 1 = тонкая, но живая вертикаль (бот в Telegram
осмысленно отвечает голосом и текстом). Всё остальное наслаивается без перепиливания базы.

База: агентная оболочка **Hermes Agent** (NousResearch) — даёт Telegram-бота,
голос/vision, cron, shell/file-инструменты, роутинг моделей. Мы её настраиваем под
клиента и добавляем навыки: память, код/тексты, конвейер автопостинга.

> **Где смотреть прогресс**: текущий статус всех этапов — в [`STATUS.md`](STATUS.md).
> Внутри каждого этапа ниже — чекбоксы конкретных acceptance-пунктов. Закрытие этапа
> сопровождается git-тегом `stage-N-done`.

| # | Этап | Главный артефакт | Зависит от |
|---|---|---|---|
| 0 | Каркас: hermes-agent поднят локально | Бот отвечает «привет» в Telegram | — |
| 1 | Живой мозг: текст + голос + стиль | Голосовое → осмысленный ответ через OpenRouter | 0 |
| 2 | Долгосрочная память | Факт сказан → агент помнит в новой сессии | 1 |
| 3 | Навык «код и тексты» | Запрос отчёта → приходит .docx/.csv файлом | 1 |
| 4 | Контент-таблица + парсинг Tilda | Ссылка Tilda → запись с товаром в Postgres | 2 |
| 5 | Генерация 3 текстов + картинки | Ссылка → 3 текста + готовое фото в превью | 4 |
| 6 | Постинг через PostMyPost | Ручной триггер → пост появился в соцсети | 5 |
| 7 | Автопостинг по расписанию (cron) | Запланировал → опубликовалось само без LLM | 6 |
| 8 | Деплой на VPS | ПК выключен — бот работает 24/7 | 7 |

## Этап 0 — Каркас: hermes-agent поднят локально

**Цель**: существующая агентная оболочка склонирована, запускается локально и отвечает
в Telegram реальным ботом клиента. Без своих навыков — просто «оно живо».

**Что делаем**:
- Клонировать репозиторий hermes-agent, изучить что уже реализовано (Telegram, STT, vision, cron, инструменты).
- Заполнить `.env` реальными доступами клиента из `доступы.txt`: бот `@Mironov_AgentBot`, `OPENROUTER_API_KEY`, `ALLOWED_USER_IDS=5183294551`.
- Поднять зависимости, запустить агента локально на Windows.

**Критерии приёмки** (закрытие → tag `stage-0-done`):
- [ ] Репозиторий hermes-agent склонирован, зафиксировано в `docs/` что в нём уже есть (карта возможностей).
- [ ] `.env` заполнен прод-доступами клиента; секреты не попадают в git (`.gitignore`).
- [ ] Бот `@Mironov_AgentBot` запущен локально и отвечает на текстовое сообщение от Mika (id 5183294551).
- [ ] Бот игнорирует сообщения от чужих user_id (защита shell-доступа работает).

## Этап 1 — Живой мозг: текст + голос + стиль

**Цель**: первый осязаемый результат — бот осмысленно общается голосом и текстом
через OpenRouter, в нужном стиле; код выдаёт по правилу (мелкий — в чат, крупный — файлом).

**Что делаем**:
- Подключить модель OpenRouter (DeepSeek V4 Pro) как основной «мозг».
- Решить распознавание голосовых **без OpenAI** (OpenRouter audio-модель / SYNTX.AI / альтернатива) — см. блокер-риск.
- Настроить системный промпт / стиль общения агента.
- Базовое правило кода: мелкий фрагмент → блок с подсветкой в чат; объёмный → файл-документ.

**Критерии приёмки** (закрытие → tag `stage-1-done`):
- [ ] Текстовый вопрос → осмысленный ответ через OpenRouter (DeepSeek V4 Pro).
- [ ] Голосовое сообщение → корректно распознано → осмысленный ответ (без OpenAI-ключа).
- [ ] Просьба «напиши маленький скрипт» → код приходит блоком с подсветкой в чат.
- [ ] Просьба «напиши большой скрипт» → код приходит файлом-документом.
- [ ] Тон/стиль ответов соответствует согласованному с клиентом.

## Этап 2 — Долгосрочная память

**Цель**: агент сохраняет факты/привычки/договорённости о пользователе в БД и выборочно
достаёт их по необходимости (не грузит всю историю в каждый запрос).

**Что делаем**:
- Поднять Postgres (локально), спроектировать схему таблиц памяти (факты, теги, источник, дата).
- Навык записи факта (явно «запомни…» и неявно из диалога) и навык выборочной подгрузки релевантных фактов в контекст.

**Критерии приёмки** (закрытие → tag `stage-2-done`):
- [ ] «Запомни, что …» → факт появился записью в Postgres (id виден).
- [ ] В новом диалоге агент использует ранее сохранённый факт в ответе.
- [ ] В контекст подгружаются только релевантные факты, а не вся таблица (выборочность).
- [ ] «Что ты обо мне помнишь?» → агент перечисляет сохранённые факты.

## Этап 3 — Навык «код и тексты»: docx / csv

**Цель**: агент генерирует деловые документы — КП в `.docx` и отчёты в `.csv` — и присылает файлом в чат.

**Что делаем**:

- Отправка готового файла документом в Telegram.

**Критерии приёмки** (закрытие → tag `stage-3-done`):
- [ ] «Сделай КП по …» → приходит валидный `.docx`, открывается в Word.
- [ ] «Сделай отчёт-таблицу …» → приходит валидный `.csv`, открывается в Excel.
- [ ] Содержимое документа соответствует запросу (не заглушка).

## Этап 4 — Контент-таблица + парсинг Tilda

**Цель**: по ссылке на товарную страницу Tilda агент достаёт данные товара и кладёт
их в управляющую таблицу контента в Postgres.

**Что делаем**:
- Спроектировать таблицу контента (товар, исходные тексты/фото, статус, площадки, время постинга, ссылки на публикации).
- Навык парсинга страницы Tilda: название, описание, фото товара.

**Критерии приёмки** (закрытие → tag `stage-4-done`):
- [ ] Ссылка Tilda → в таблице контента появляется запись с названием, описанием и URL фото товара.
- [ ] Схема таблицы покрывает весь жизненный цикл поста (черновик → запланирован → опубликован).
- [ ] Некорректная/недоступная ссылка → понятная ошибка в чат, мусорной записи нет.

## Этап 5 — Генерация 3 текстов + обработка картинки

**Цель**: из распарсенного товара агент генерирует 3 версии текста для соцсетей и
готовит изображение через kie.ai (gpt-image-2: дорисовка фона, обрезка).

**Что делаем**:
- Генерация 3 версий поста через OpenRouter.
- Генерация/обработка фото через kie.ai (createTask → polling recordInfo → resultUrls).
- Превью результата в чат на подтверждение.

**Критерии приёмки** (закрытие → tag `stage-5-done`):
- [ ] Из записи контента → 3 различимые версии текста для соцсетей.
- [ ] kie.ai возвращает готовое изображение (фон дорисован/обрезка), URL сохранён в таблице.
- [ ] Агент присылает в чат превью: 3 текста + картинку.
- [ ] Выбранный вариант фиксируется в таблице контента.

## Этап 6 — Постинг через PostMyPost

**Цель**: подтверждённый контент реально публикуется в соцсети через PostMyPost API
(3-этапная схема: загрузка фото → проверка → публикация).

**Что делаем**:
- Интеграция PostMyPost API (тариф «Продвинутый 5»): загрузка изображения, проверка статуса, публикация.
- Привязка площадок (Telegram / Instagram / Facebook) из аккаунта клиента.

**Критерии приёмки** (закрытие → tag `stage-6-done`):
- [ ] Ручной триггер публикации → пост реально появился хотя бы в одной соцсети.
- [ ] Статус публикации и ссылка на пост записаны в таблицу контента.
- [ ] Ошибка публикации (отзыв токена соцсети и т.п.) → понятное сообщение, статус «ошибка», без молчаливой потери.

## Этап 7 — Автопостинг по расписанию (cron)

**Цель**: публикация по расписанию идёт **сама**, скриптом по cron, без трат токенов LLM.

**Что делаем**:
- Cron-скрипт: берёт из таблицы записи со статусом «запланировано» и наступившим временем → публикует через PostMyPost → обновляет статус.
- Назначение времени постинга агентом при подготовке контента.

**Критерии приёмки** (закрытие → tag `stage-7-done`):
- [ ] Запланированный на конкретное время пост публикуется автоматически без участия человека.
- [ ] Cron-постинг не вызывает LLM (только БД + PostMyPost API).
- [ ] После публикации статус в таблице → «опубликовано» с временем и ссылкой.
- [ ] Повторный прогон cron не публикует один и тот же пост дважды (идемпотентность).

## Как писать критерии приёмки

Критерий — **наблюдаемое поведение**, которое клиент может проверить руками, а не внутренняя задача.
Хороший набор критериев = сценарий приёмочной проверки. Когда все `[x]` — этап реально готов к тегу.
