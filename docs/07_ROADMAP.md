# Дорожная карта реализации — ИИ-агент «Хермес» (Mironov)

13 этапов от настройки базовой агентной оболочки до прод-готовности на VPS. Каждый
этап заканчивается **демонстрируемым результатом** (что можно потрогать руками).

Ключевая идея: **MVP-first**. Этап 1 = тонкая, но живая вертикаль (бот в Telegram
осмысленно отвечает голосом и текстом). Всё остальное наслаивается без перепиливания базы.

База: агентная оболочка **Hermes Agent** (NousResearch) — это НЕ обёртка над API-запросом
к модели, а агент со **skills**: ему даются инструменты и навыки, а *как* выполнить задачу
он решает сам (вызов shell, создание файлов/скриптов, cron и т.д.). Оболочка уже даёт
Telegram-бота, голос/vision, cron, shell/file-инструменты, роутинг моделей. Мы её настраиваем
под клиента и **добавляем навыки** (skills) + cron-обвязки для рутины: память, код/тексты,
гибкий навык контента и автопостинга.

**Принцип постинга — гибкий сценарий, а не жёсткий пайплайн.** Вход — это свободная команда
ИЛИ ссылка (в т.ч. Tilda) ИЛИ описание. Агент сам уточняет недостающее, готовит текст +
картинку, спрашивает *куда* и *когда* публиковать — как обычный диалог. Tilda-парсинг — лишь
один из возможных источников внутри навыка, а не обязательный шлюз. Рутину (публикацию по
времени) выносим в cron-скрипт без трат токенов LLM.

> **Где смотреть прогресс**: текущий статус всех этапов — в [`STATUS.md`](STATUS.md).

## Этап 1 — Живой мозг: текст + голос + стиль

**Цель**: первый осязаемый результат — бот осмысленно общается голосом и текстом
через OpenRouter, в нужном стиле; код выдаёт по правилу (мелкий — в чат, крупный — файлом).

> **Архитектурное ограничение (сервер 1 ядро / 1 ГБ ОЗУ)**: никакого локального инференса.
> STT и vision — **только по API**. Локальный faster-whisper исключён.
> - **STT (голос)** → API-провайдер, не OpenAI (его нет). Выбран **Groq** (free tier, Whisper large-v3-turbo). Альтернативы: Mistral Voxtral, ElevenLabs Scribe.
> - **Vision (фото)** → через **OpenRouter** (мультимодальная модель, напр. Gemini Flash) — отдельный ключ не нужен.

**Что делаем**:
- Подключить модель OpenRouter (DeepSeek V4 Pro) как основной «мозг».
- STT по API: `stt.provider: groq` (+ `GROQ_API_KEY`), local отключён.
- Vision по API через OpenRouter: задать `auxiliary.vision` (провайдер openrouter + мультимодальная модель).
- Настроить системный промпт / стиль общения агента (SOUL.md).
- Базовое правило кода: мелкий фрагмент → блок с подсветкой в чат; объёмный → файл-документ.

**Критерии приёмки** (закрытие → tag `stage-1-done`):
- [x] Текстовый вопрос → осмысленный ответ через OpenRouter (DeepSeek V4 Pro). _(подтверждено 2026-06-28)_
- [x] Голосовое сообщение → распознано по API (Groq whisper-large-v3-turbo, без локального whisper) → осмысленный ответ. _(лог 19:27:33, «Прием, слышно?»)_
- [x] Фото в чат → агент анализирует его через OpenRouter (vision по API). _(лог 19:28:45, анализ 1523 симв.)_
- [x] Просьба «напиши маленький скрипт» → код приходит блоком с подсветкой в чат. _(подтверждено вживую 2026-06-28)_

## Этап 2 — Долгосрочная память

**Цель**: агент сохраняет факты/привычки/договорённости о пользователе и выборочно
достаёт их по необходимости (не грузит всю историю в каждый запрос).

> **Механизм**: используем **встроенную память hermes** (файловая, выборочная, лёгкая для
> сервера 1ГБ — БД не нужна): `USER.md` (профиль пользователя) + `MEMORY.md` (заметки агента),
> с лимитом символов вшиваются в системный промпт каждой сессии; агент сам их пополняет/чистит.
> Плюс `session_search` — поиск по прошлым диалогам. Postgres для памяти НЕ поднимаем
> (он будет для контент-таблицы на этапе 4). Тяжёлый бэкенд (mem0/honcho) — только если
> встроенной памяти окажется мало.

**Что делаем**:
- Убедиться, что память включена (`memory_enabled`, `user_profile_enabled` в config) и агент пишет факты.
- Проверить запись факта (явно «запомни…» и неявно из диалога) и выборочную подгрузку в новой сессии.
- При необходимости подстроить лимиты/нуджи (`memory_char_limit`, `nudge_interval`, `flush_min_turns`).

**Критерии приёмки** (закрытие → tag `stage-2-done`):
- [x] «Запомни, что …» → факт сохранён в `USER.md`/`MEMORY.md`. _(«Любимые цвета: чёрный и зелёный» в USER.md, 2026-06-28)_
- [x] В новой сессии (после `/new` или сброса) агент использует ранее сохранённый факт в ответе. _(recall после /new подтверждён)_
- [x] В контекст подгружается выборочная память (профиль + заметки), а не вся история диалогов. _(компактные USER.md/MEMORY.md)_
- [x] «Что ты обо мне помнишь?» → агент перечисляет сохранённые факты. _(проверено в CLI и Telegram)_

> **Доработка по ходу**: явные «запомни» сохранялись ненадёжно (curation + короткие сессии). Добавлено жёсткое правило в `SOUL.md` — на «запомни/не забудь» агент пишет в память **немедленно**, только по-русски (DeepSeek подмешивал иероглифы — устранено).

## Этап 4 — Навык «контент»: текст + картинка (гибкий сценарий)

**Цель**: агентный навык подготовки поста. Вход свободный — команда, описание ИЛИ ссылка
(в т.ч. Tilda). Агент сам уточняет недостающее, генерирует 3 версии текста и картинку,
показывает превью, кладёт черновик в управляющую таблицу контента (Postgres).

**Что делаем**:
- Спроектировать таблицу контента в Postgres (товар/тема, версии текста, картинка, статус, площадки, время, ссылки на публикации).
- Навык генерации 3 версий текста через OpenRouter из любого входа (текст/ссылка); парсинг Tilda — как один из источников, опционально.
- Навык генерации/обработки картинки через kie.ai (gpt-image-2: дорисовка фона/обрезка; createTask → polling recordInfo → resultUrls).
- Гибкий диалог: если данных мало — агент уточняет; превью (3 текста + картинка) в чат.

**Критерии приёмки** (закрытие → tag `stage-4-done`):
- [x] «Сделай пост про …» (свободное описание) → агент уточняет недостающее и выдаёт 3 различимые версии текста.
- [x] То же по ссылке (в т.ч. Tilda) → агент достаёт суть страницы и генерит тексты.
- [x] kie.ai возвращает картинку(и): для Tilda из 1-го фото товара собирается маркетплейс-карточка (image-to-image), 2-е фото идёт как есть; для свободного брифа — обложка (text-to-image). Агент присылает превью: 3 текста + картинки.
- [x] Черновик с выбранным вариантом и всеми картинками (`images`) сохранён записью в таблице контента (id виден).

## Этап 7 — Веб-поиск: включить рабочий бэкенд

**Цель**: у агента появляется реально работающий веб-поиск. На вопрос про свежие
факты (курсы, новости, «что сейчас с…», проверка URL/цен) он вызывает `web_search`
и отвечает по найденному, а не по памяти модели.

> **Исходное состояние (диагностика 2026-07-01)**: веб-поиск **выключен полностью**.
> В `%LOCALAPPDATA%\hermes\.env` все ключи поиска закомментированы (Firecrawl, Tavily,
> Exa, Parallel, Brave), `SEARXNG_URL` не задан; в `config.yaml` секции `web:` нет.
> Auto-detection hermes не находит ни одного бэкенда, а единственный бесплатный
> без ключа **DDGS (DuckDuckGo)** в цепочку авто-детекта **не входит** → сам не включается.
> Именно поэтому агент не ищет и выдумывает (см. этап 8). Свой поисковик писать не надо:
> hermes даёт `web_search`/`web_extract` из коробки — нужно выбрать и включить бэкенд.

**Что делаем**:
- Выбрать бэкенд под сервер 1 ядро / 1 ГБ и бюджет клиента (решение с клиентом). Кандидаты:
  - **DDGS** — бесплатно, без ключа, search-only, качество/лимиты средние (быстрый MVP-fallback).
  - **Tavily / Exa** — 1000 запросов/мес free, AI-оптимизированы, есть `web_extract` (рекомендуется как основной).
  - **Firecrawl** — дефолт hermes, search+extract, 500 кредитов/мес free.
  - **SearXNG self-hosted** — free без лимитов, но +контейнер на слабый сервер, search-only.
  - Комбо допустимо: `search_backend` (free) + `extract_backend` (качественный).
- Прописать `web.backend` (или `search_backend`/`extract_backend`) в `config.yaml` + ключ в `.env`.
- Убедиться, что `web_search`/`web_extract` доступны боту (не только CLI) и внутри `execute_code`-песочницы (env passthrough при необходимости).
- Живой прогон: пара свежих вопросов через Telegram/CLI → агент ищет и цитирует источник.

**Критерии приёмки** (закрытие → tag `stage-7-done`):
- [x] `hermes setup` / модуль `tools.web_tools` показывает активный бэкенд (не «none»). _(2026-07-01: `✅ Web backend: tavily`)_
- [x] Вопрос про свежий факт (курс/новость/«что сейчас с…») → агент вызывает `web_search` и отвечает по найденному, с указанием источника (URL). _(Kira подтвердила вживую 2026-07-01: бот реально ищет)_
- [x] `web_extract` (если бэкенд его поддерживает) достаёт содержимое конкретной страницы по URL. _(2026-07-01: Tavily extract вернул содержимое example.com; search вернул живую погоду Москвы)_

## Этап 8 — Запрет выдумок (anti-hallucination)

**Цель**: агент перестаёт сочинять факты. Если не уверен или спрашивают про свежие/
проверяемые данные — он **сначала ищет** (этап 7), а если поиск недоступен или ничего
не нашёл — честно говорит «не знаю / не нашёл», а не выдаёт правдоподобную выдумку.

> Зависит от этапа 7: без рабочего поиска «не выдумывай» превращается в «всегда отвечай
> "не знаю"». Сначала даём инструмент, потом правило им пользоваться.

> Механизм родной, писать движок не нужно. Кандидаты, выбор — на этапе:
> **Mixture of Agents** (`moa` — виртуальный провайдер: агрегатор пишет ответ и
> вызывает инструменты, reference-модели дают анализ; есть `/moa <промпт>` —
> разовый прогон с возвратом на прежнюю модель) и **delegation** (подзадача на
> другой модели). Плюс точечные слоты `auxiliary.goal_judge` / `background_review`.
> MoA гоняет reference-модели на **каждом** вызове главной модели — поэтому
> «всегда включённый» пресет как модель по умолчанию сразу отпадает по деньгам.

**Что делаем**:
- Выбрать механизм (MoA-пресет vs delegation) по критерию «подключается только на
  сложном» и зафиксировать выбор в STATUS.
- Настроить: агрегатор — основная модель, критик — Sonnet 5 через OpenRouter.
- Правило в SOUL.md: что считаем сложной задачей.
- Посчитать стоимость: Sonnet сильно дороже основной модели, а на счету клиента ~$20 —
  поэтому этап идёт **после** `/balance` (этап 13), чтобы расход было видно.

> **Механизм выбран (2026-07-16): делегация.** MoA отпал по коду: `/moa` намеренно
> **не инструмент модели** (`agent/moa_loop.py`), его зовёт только человек — агент сам
> критика не подключит; плюс reference-модели гоняются перед **каждой** итерацией.
> `auxiliary.goal_judge` работает только в `/goal`-лупе, `background_review` пишет
> память после каждого хода — оба не критикуют ответ. У делегации свои границы, их
> учли: модель субагента задаётся **только глобально** (`delegation.model`, не на вызов),
> делегация top-level **всегда фоновая** (критика приходит вторым сообщением), субагент
> **не видит историю** — черновик передаётся в `context`.
> **Основная модель на проде — Gemini 3 Flash**, не DeepSeek (см. шапку STATUS).

**Критерии приёмки** (закрытие → tag `stage-15-done`):
- [x] На сложной задаче видно, что подключилось второе мнение, и ответ от него улучшился. _(живая цепочка в Telegram 16.07 05:10–05:11, лог gateway: Kira просит функцию на Python → агент отвечает (1463 симв.) → `ASYNC DELEGATION BATCH COMPLETE — deleg_13cc76df` → **второе сообщение** с итогом критики (2229 симв.). Содержательность критики — на КП оптовикам критик нашёл реальную логическую ошибку в прогрессии скидок)_
- [x] На простой задаче («привет», «который час») критик не подключается. _(машинно: «привет», «спасибо», «который час», «погода», напоминание → 0 вызовов `delegate_task`; на проде «Привет! Как настроение?» → CRITIC_ABSENT)_
- [x] Расход после включения критика виден через `/balance` и остаётся приемлемым. _(16.07: остаток $15.65 из $48, расход за день $0.55 — вместе с тестовыми прогонами; один вызов критика ≈ 1 цент)_
- [x] Работает на проде. _(маршрут на Sonnet 5 доказан жёстко: при заведомо неверной `delegation.model` OpenRouter ответил «not a valid model ID», притом что родитель шёл на другой модели)_

> **Чем подтверждено**: доставка второго сообщения — живым Telegram-обменом (лог gateway),
> остальное — машинными прогонами на проде. Отдельного UAT Микой не проводилось —
> закрыто по решению Анастасии 2026-07-16.

## Этап 16 — Создание навыков с нуля (skill-creator)

**Цель**: клиент говорит «сделай навык, который …» — агент расспрашивает, что за навык и
когда он должен срабатывать, показывает черновик и после подтверждения заводит рабочий навык.
Аналог `/skill-creator` у Claude Code.

> **Отменяет решение этапа 11.** Там объём был сознательно урезан до «только правка
> существующих навыков, создание с нуля не входит» (осторожный вариант, решение клиента
> 2026-07-02). Клиент 2026-07-16 попросил обратное. Этап 11 и его тег **не переписываем**
> задним числом — запрет снимается явно здесь.

> **Движок писать не нужно** — это третий такой этап подряд (ср. 10, 11, 13).
> `skill_manage(action="create")` уже в ядре Telegram-тулсета, и на этапе 11 полный цикл
> `create→patch→readback→delete` был **проверен машинно**. Создание технически работает уже
> сейчас; оно заблокировано только правилом в навыке `skill-editing` и в SOUL.md. Работа этапа =
> навык-гид + снятие запрета + обвязка синхронизации.

**Что делаем**:
- Навык-гид `hermes-skills/meta/skill-creator`: интервью (что за навык, по каким фразам
  срабатывает, шаги, нужны ли скрипты и секреты) → черновик `SKILL.md` → **подтверждение
  человека** → `skill_manage(create)` → `skill_view` для самопроверки → отчёт.
- Снять запрет в `meta/skill-editing` и в SOUL.md, оставив ссылку на новый навык.
- **Гейт — интервью + подтверждение** (решение клиента 2026-07-16): агент не создаёт навык
  молча. Штатный write-gate hermes не включаем — он бы затронул и правки этапа 11.
- Автосинк созданных на проде навыков в git (решение клиента 2026-07-16).

> **Три риска, вскрытые разведкой (2026-07-16), — их закрывает навык, а не движок**:
> 1. **Слот в меню Telegram.** Каждый навык = команда; лимит `max_commands` = 65, занят 61
>    (этап 13). Навык, который плодит навыки, за 4 штуки упрётся в потолок и начнёт **молча
>    вытеснять** существующие команды — ровно регрессия этапа 13. Навык обязан сверять
>    `getMyCommands` и предупреждать при подходе к лимиту.
> 2. **Git vs прод.** `skill_manage` пишет в `/root/.hermes/skills`, источник правды — репо
>    `hermes-skills/`. `rsync` в `deploy.sh` идёт **без `--delete`**, поэтому созданный агентом
>    навык деплой переживёт (комментарий в `deploy.sh` про «перезапишутся» верен только для
>    одноимённых), но в git его нет → потеря при пересоздании сервера.
> 3. **Автосинк не имеет права писать в master.** `deploy.sh` делает `git reset --hard
>    origin/master` в `/opt/pers_herms_at` — коммиты, сделанные в том же рабочем дереве, он
>    снесёт. Синк идёт из отдельного клона в отдельную ветку, мержит человек.

**Критерии приёмки** (закрытие → tag `stage-16-done`):
- [x] «Сделай навык, который …» → агент задаёт уточняющие вопросы, а не создаёт молча. _(прогон на проде «сделай навык, который считает НДС»: агент задал 3 вопроса — ставка, начислять или выделять, формат — и пообещал черновик на утверждение; навык не создан)_

## Как писать критерии приёмки

Критерий — **наблюдаемое поведение**, которое клиент может проверить руками, а не внутренняя задача.
Хороший набор критериев = сценарий приёмочной проверки. Когда все `[x]` — этап реально готов к тегу.
