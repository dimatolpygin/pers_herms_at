# Метрика делегирования

Здесь живут замеры, которыми проверяется числовой критерий приёмки этапа 19:
**из 10 профильных задач подряд Гера отдаёт профилю не меньше 9.**

Замер снимает `scripts/delegation_metric.py` — один и тот же скрипт для «до» и «после»,
иначе цифры несравнимы.

## Файлы

| Файл | Что это |
|---|---|
| `delegation_baseline_2026-08-27.md` | Замер «как есть» до начала работ. **0 из 18.** |
| `review_docs_2026-08-27.json` | Ручные вердикты к baseline: какие задачи автоматика подобрала зря |

## Как повторить замер

Скрипт читает боевую `state.db`, поэтому запускается на сервере:

```bash
scp scripts/delegation_metric.py root@89.125.17.86:/root/hermes-metrics/
ssh root@89.125.17.86 'cd /root/hermes-metrics && \
  python3 delegation_metric.py --domain docs --review review.json \
    --out after.md --json after.json'
```

Для приёмки — последние десять задач:

```bash
python3 delegation_metric.py --domain docs --review review.json --last 10 --out accept.md
```

База открывается только на чтение, gateway трогать не нужно.

## Почему цифра считается именно так

**Единица счёта — задача, а не сообщение.** Первый вариант скрипта считал по репликам
и дал заведомо неверную картину: реальная работа клиента выглядит как разговор —
«сделай КП в ворде» → «а ворд где?» → «файл ворд пожалуйста» → «это 11-й вариант, ты
потратил кучу моего времени». Это одна задача из десятка реплик, причём половина реплик
без глагола, и по отдельности они не ловятся. Задача собирается из подряд идущих реплик
по теме; пауза больше 45 минут или больше двух реплик не по теме — уже следующая задача.

**`delegate_task` не засчитан как делегирование профилю.** Он порождает ребёнка с
тулсетами и моделью родителя — это тот же Гера в другом окне, а не специалист со своей
моделью и своими навыками. Засчитывать его было бы подтасовкой в свою пользу: в baseline
таких случаев четыре, и они бы превратили честный 0 % в 22 %.

**В знаменателе только задачи, где работа реально делалась.** Если Гера отговорился
текстом и ничего не создал, делегировать было нечего — такие задачи считаются отдельной
строкой и в долю не входят.

**Машинный текст вырезается до сопоставления.** Внутри сообщений с `role='user'` лежат
не только слова клиента: пересказ картинки от vision, имя приложенного файла, служебные
врезки движка (`[ASYNC DELEGATION BATCH COMPLETE…]`, `[CONTEXT COMPACTION…]`), цитаты
собственных реплик агента. В первом прогоне из 263 «задач» 42 оказались врезками движка,
60 — описаниями картинок, 41 — именами файлов. Считать по ним нельзя.

**Отбор проверяется руками.** Скрипт только предлагает список; вердикты правятся через
`--review`. Из 45 автоматически отобранных задач при пересмотре снято 27 — дубли сессий,
разговоры про модели и бюджет, задачи чужих профилей (SEO, finance). Цифру, которую
нельзя перепроверить глазами, клиент справедливо не примет.

## Результат замера «до»

За 02.07 → 27.08, по 2494 ходам в Telegram:

| | |
|---|---:|
| Профильных задач `docs` с реальной работой | 18 |
| Отдано профилю-специалисту | **0** |
| Отдано безымянному субагенту `delegate_task` | 4 |
| Гера сделал сам | 14 |
| **Доля делегирования профилю** | **0.0 %** |

Ноль — не придирка к формулировке, а состояние системы: шесть профилей клиент завёл
21 августа, но ни один ни разу не запускался (`hermes profile list` — все `stopped`,
`kanban.db` пуст). Пути «отдать работу профилю» на момент замера просто не существовало.
Отсюда и берётся работа этапа 19: сначала построить путь, потом заставить им пользоваться.
