# Как завести новый профиль-агента

Инструкция для Мики. Рассчитана на то, что вы заводите профиль **сами**, без нас.
Профили Health и Finance, о которых вы говорили, встают по этому же пути.

Занимает это минуты, а не дни. Замер на профиле `dev` 28.08.2026: **2.7 секунды**
на саму сборку. Остальное время — придумать, что профиль должен уметь.

---

## Коротко: три шага

1. Дописать блок в `profiles/registry.yaml` (это описание профиля, обычный текст).
2. `python3 scripts/profile_forge.py render <имя>` — собрать файлы профиля.
3. На сервере: `python3 scripts/profile_forge.py install <имя>` — поставить.

Потом обязательно четвёртый:

4. `python3 scripts/profile_acceptance.py <имя> --live` — приёмка.
   **Профиль без пройденной приёмки не выпускается.** Не потому что бюрократия,
   а потому что каждый пункт этого чеклиста — отказ, который уже случался на
   вашем сервере и стоил времени.

---

## Шаг 1. Описать профиль в реестре

Откройте `profiles/registry.yaml` и допишите блок по образцу. Вот минимальный —
на примере профиля здоровья:

```yaml
  health:
    title: "Здоровье"
    model: deepseek/deepseek-v4-pro
    critic: qwen/qwen3.7-max
    critic_why: >-
      Cross-check DeepSeek -> Qwen. Там, где речь о дозировках и анализах,
      критик обязан быть из другой семьи моделей.
    describe: >-
      Здоровье: расшифровка анализов, ведение дневника показателей, подготовка
      вопросов к врачу, отслеживание приёма препаратов.
      Не сюда: счета из клиники и налоговые вычеты — это docs.
    duties:
      - "Расшифровка результатов анализов"
      - "Дневник показателей и динамика"
      - "Подготовка вопросов к приёму"
    artifacts: /root/.hermes/artifacts/health
    env_passthrough:
      - OPENROUTER_API_KEY
    skills:
      ocr-and-documents: productivity/ocr-and-documents
```

Что здесь важно и почему:

**`describe` — это не описание для красоты.** По нему Гера выбирает, кому отдать
задачу. Фраза «**Не сюда:** …» обязательна: когда профилей восемь, зоны начинают
пересекаться (счёт из клиники — это Health, Finance или docs?), и «не сюда» —
единственное, что удерживает задачу от ухода не туда. Скрипт проверки откажется
принимать блок без неё.

**`critic` должен быть из другой семьи моделей.** DeepSeek проверяет DeepSeek —
это не проверка, он повторит собственную ошибку. Скрипт это тоже проверяет.

**`artifacts` — абсолютный путь.** Профиль работает во временном каталоге,
который **удаляется** после завершения задачи. Файл, записанный внутрь него,
пропадёт вместе с ним, и задача будет выглядеть сделанной при отсутствующем
результате. Путь в `artifacts` лежит снаружи.

**`skills` — только то, что профилю реально нужно.** Слева имя, справа путь в
общем каталоге навыков. Чем короче список, тем лучше профиль работает: у Геры
промпт 86 КБ и он «забывает» инструкции, у профиля `dev` — 14 КБ.
Навыки при этом **не копируются**, а подключаются ссылкой на общий каталог.
Удалить навык у профиля можно спокойно; удалить сам навык — нельзя, он сломается
у Геры и во всех профилях сразу.

Проверить, что блок написан правильно, не устанавливая ничего:

```bash
python3 scripts/profile_forge.py --check
```

## Шаг 2. Собрать файлы

```bash
python3 scripts/profile_forge.py render health
```

Появится `profiles/health/` с четырьмя файлами: `SOUL.md` (характер и правила
профиля), `config.yaml` (модель и предохранители), `distribution.yaml` (паспорт
для установки), `skills.txt` (опись навыков). Их **не надо править руками** —
они собираются из реестра, и ручная правка потеряется при следующей сборке.
Нужно поменять — меняйте реестр.

Если профилю нужно что-то, чего в шаблон не вложишь — реквизиты, образцы,
особые правила, — положите это в `profiles/_extra/health.md`. Этот текст
допишется в конец `SOUL.md` как есть. Так сделано у `docs`: там лежат реквизиты
ИП и рабочий вызов критика.

Закоммитьте — профиль теперь живёт в git и переживёт падение сервера.

## Шаг 3. Поставить на сервер

```bash
cd /opt/pers_herms_at && git pull
python3 scripts/profile_forge.py install health
```

Что произойдёт: профиль установится штатной командой hermes, получит доступ к
ключам, к нему подключатся навыки из списка, создастся каталог артефактов,
Гере обновится справочник «кому какая задача».

Посмотреть, что будет сделано, ничего не меняя: добавьте `--dry-run`.

## Шаг 4. Приёмка

```bash
python3 scripts/profile_acceptance.py health --live
```

Без `--live` — пятнадцать быстрых проверок за секунду. С `--live` скрипт заводит
профилю **настоящую задачу**, ждёт, пока он её сделает, и проверяет, что файл
действительно появился. Это единственная проверка, которая доказывает, что
профиль работает, а не просто установлен. Занимает столько, сколько занимает
задача — у `dev` вышло 49 секунд.

Чтобы живая проверка была осмысленной, допишите профилю в реестр приёмочную
задачу:

```yaml
    acceptance_probe:
      title: "Приёмка health: расшифровка анализа"
      body: >-
        Приёмочная проверка, не боевая задача. ...
      max_runtime: 20m
```

**В приёмочных задачах не выдумывайте реквизиты организаций.** Гера прогоняет
ИНН и ОГРН через контрольную сумму, лезет в реестр и отказывается работать
с несуществующими — правильное поведение, но проверку оно срывает. Пишите либо
настоящие данные, либо задачу, где реквизиты не нужны.

Результат: `ПРОШЁЛ` — профиль можно выпускать. `НЕ ПРОШЁЛ (N блокеров)` —
в выводе написано, что именно и почему это блокер.

## Что делать дальше с готовым профилем

**Изменить профиль** — поправьте реестр, `render`, закоммитьте, на сервере:

```bash
git pull && python3 scripts/profile_forge.py install health
```

Память профиля, его сессии и ключи при этом не трогаются — переустанавливается
только описание и настройки.

**Заставить Геру отдавать задачи новому профилю.** Гера по своей воле не
делегирует: замерено, что при наличии собственного навыка он в 10 случаях из 10
сначала тянется сделать сам. Работает не уговор, а сторож — файл
`hooks/profile_guard.json`. Допишите туда блок:

```json
    "health": {
      "enabled": true,
      "what": "здоровье: анализы, показатели, вопросы врачу",
      "skills": ["ocr-and-documents"],
      "markers": []
    }
```

`skills` — навыки, открытие которых у Геры означает «полез делать сам».
`enabled: false` — блок описан, но не действует; так профиль сначала проходит
приёмку, и только потом Гере что-то запрещают.

**Посмотреть, кому что уходит:** `hermes kanban list`.
**Померить, как Гера делегирует:** отчёт собирается сам по понедельникам,
журнал — `/root/hermes-metrics/delegation_log.md`.

## Чего этот конвейер не делает

Честная граница, чтобы не было сюрпризов:

* **Содержание профиля — ваше.** Конвейер гарантирует, что профиль поднимется,
  получит задачу и пройдёт чеклист. Насколько хорошо он разбирается в анализах
  или в налогах — зависит от того, что вы напишете в `duties`, `_extra` и какие
  навыки подключите. Приёмка содержания — отдельная работа.
* **Критик пока вызывается самим профилем** по инструкции в `SOUL.md`, а не
  штатным механизмом `kanban swarm`. Для `docs` это проверено и работает;
  правильный вариант со swarm в оплаченный объём не входит.
* **Приватность на уровне профиля не сделана.** Сейчас все профили смотрят в
  один общий файл ключей. Для Health это, скорее всего, придётся менять —
  это отдельная позиция, о ней надо говорить до того, как туда поедут медданные.
* **Общая память между профилями не разведена** на «общее о вас» и «личное
  профиля». Вы про это уже спрашивали — тоже отдельная позиция.
