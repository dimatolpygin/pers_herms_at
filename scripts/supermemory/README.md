# Разовая заливка накопленной памяти в supermemory (этап 17)

Скрипты запускались **один раз** на проде 2026-08-06 при подключении supermemory.
Держим их в репо, чтобы миграцию можно было повторить на новом сервере.

Запускать интерпретатором hermes (там стоит SDK и читается `.env`):

```bash
/usr/local/lib/hermes-agent/venv/bin/python migrate_conversation.py
/usr/local/lib/hermes-agent/venv/bin/python migrate_documents.py
```

## Почему два скрипта, а не один

Это была главная находка этапа — **у supermemory два разных пути приёма данных,
и они дают разный результат**:

| Скрипт | Куда пишет | Что получается |
|---|---|---|
| `migrate_documents.py` | `POST /v3/documents` | документ ложится целиком и ищется **только** поиском по документам |
| `migrate_conversation.py` | `POST /v4/conversations` | запускается извлечение фактов → появляются **memories** и профиль |

Плагин hermes ищет через `search.memories` и читает у результата поле `memory`.
У документных результатов текст лежит в `chunk`, а `memory` пустое — то есть
**залитые документами файлы плагин находит, но прочитать не может**. Поэтому
реальную память даёт `migrate_conversation.py`; документный ингест оставлен как
просматриваемый архив в UI supermemory.

Отсюда же настройка `search_mode: memories` в `~/.hermes/supermemory.json`:
в режиме `hybrid` три слота выдачи из пяти уходили на документы с пустым текстом.

## Что намеренно НЕ заливается

`notes/mika-passwords.md` — пароли в стороннее облако не отправляем
(константа `EXCLUDE` в обоих скриптах).

## Задержка

Извлечение фактов асинхронное: документ получает `status: done` почти сразу, но
факты и профиль появляются **через 1.5–3 минуты**. Сразу после заливки поиск
честно отдаёт пусто — это не ошибка.
