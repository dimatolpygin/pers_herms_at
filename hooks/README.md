# hooks/ — сторож зон ответственности

`profile_guard.py` — хук `pre_tool_call` у **Геры**. Не даёт ему молча делать
работу профиля своими руками: ловит вызов и возвращает не ошибку, а инструкцию
«передай в профиль через `kanban_create`».

Профилям хук не ставится никогда — внутри профиля та же работа законна.

## Зачем он вообще, если есть навык

Замерено 27.08.2026. После того как транспорт заработал (этап 19.2) и появился
навык `meta/profile-delegate`, Гера на просьбу «сделай счёт-оферту» **дважды**
пошёл делать сам: открыл `business-documents`, потратил 13 и 20 вызовов —
браузер, vision, чтение прошлых счетов — и в навык делегирования не заглянул
ни разу. Навык — это совет; пока есть короткий путь, модель выбирает его.

Сигнал для блокировки выбран по тому же замеру: в обоих прогонах **первым же
вызовом** шёл `skill_view business-documents`. Ловить надо там — до того, как
он начал, а не на моменте записи файла.

## Что блокируется

| Правило | Сигнал | Пример из замера |
|---|---|---|
| `skill` | `skill_view` навыка из чужой зоны | `skill_view business-documents` |
| `skill-path` | путь навыка в команде — обход `skill_view` | `python3 .../business-documents/scripts/validate_ru_requisites.py` |
| `marker` | та же работа руками, без навыка | `from docx import Document` |

Правило `marker` — главное на будущее: после этапа 19.4 документные навыки у
Геры выключены, и написать `python-docx` руками останется единственным обходом.

**Инструменты не отбираются.** `terminal`, `execute_code`, `write_file`, `patch`
у Геры остаются: у `delegate_task` дети наследуют тулсеты родителя, срежем руки
Гере — срежем и детям (инвариант 3 в `CLAUDE.md`). Блокируется узкий сигнал.

Команды чтения и переноса (`ls`, `cat`, `cp`, `file`, …) пропускаются: готовый
файл профиля надо уметь посмотреть и переслать.

## Как добавить профиль

Правится только `profile_guard.json`, код не трогается:

```json
"health": {
  "enabled": false,
  "what": "здоровье: анализы, приёмы, назначения",
  "skills": ["health-tracker"],
  "markers": []
}
```

`enabled: false` — блок описан, но не применяется. Профиль сначала заводится и
проходит `profile-acceptance`, и только потом флаг переводится в `true`. Иначе
Гере запретят работу, которую ещё некому делать.

**В `skills` не пишутся инфраструктурные навыки профиля.** У `docs` лежат
`balance` и `s3-upload` — Гера пользуется ими законно, и в карте их нет.

## Установка

Файлы едут на прод через `deploy/deploy.sh` (шаг «sync хуков»). Блок в
`/root/.hermes/config.yaml` правится один раз руками — конфиг не в git:

```yaml
hooks_auto_accept: true          # gateway не TTY, согласие иначе не дать
hooks:
  pre_tool_call:
    - command: /usr/bin/python3 /root/.hermes/hooks/profile_guard.py
      matcher: "skill_view|terminal|execute_code|write_file|patch"
      timeout: 10
```

`matcher` — regex по **имени тула** (fullmatch), не по содержимому.

Применить: `systemctl reload hermes-gateway` (у юнита `ExecReload=kill -USR1` —
штатный мягкий рестарт). Согласие на хук записывается в
`~/.hermes/shell-hooks-allowlist.json` при регистрации, то есть при первом
старте агента после правки конфига, а не командой `hooks doctor`.

Проверка — штатная: `hermes hooks list`, `hermes hooks doctor`,
`hermes hooks test pre_tool_call`.

## Журнал

Каждая блокировка пишется строкой JSON в `/root/.hermes/logs/profile_guard.jsonl`
(`rule`, `tool`, `profile`, `detail`, `session`, `ts`). По нему видно, за что
именно Геру остановили — без этого «хук работает» остаётся словами.

## Отказ безопасен в одну сторону

Любая ошибка внутри хука — пропустить вызов (фейл-опен) и написать в stderr.
Сломанный сторож не имеет права остановить агента клиента. Обратная сторона:
если хук молча не работает, снаружи это выглядит как «Гера опять делает сам» —
поэтому проверять надо журналом, а не наблюдением.
